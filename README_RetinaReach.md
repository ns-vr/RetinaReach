# RetinaReach
### Quality-aware retinal screening, built for the real world

RetinaReach is a retinal-screening project focused on one problem that can get overlooked when we talk about medical AI: **what happens when the image itself is not good enough to trust?**

A model might perform well on a clean benchmark image, but images captured during a busy screening camp can be blurry, poorly lit, or off-centre. If a system still produces a confident-looking result, it can create the wrong kind of reassurance. If it simply rejects the image, the person taking it is left guessing what to fix.

RetinaReach is designed around a more careful workflow. It checks image quality first, explains when an image may need to be captured again, and treats uncertain results as a reason for human review rather than pretending the model is always right.

The project was developed for the **DataNova 2026 Healthcare & Social Impact / Responsible AI track**.

> **Important:** RetinaReach is a prototype, not a clinically validated medical device. Its current backend includes basic image-quality heuristics and a place to connect a separately deployed model. Unless that model service has been configured and evaluated, RetinaReach does not produce a diabetic-retinopathy diagnosis. Do not use it to make patient-care decisions.

## Why build this?

Diabetic retinopathy can lead to preventable vision loss, and early screening matters. But access to specialist eye care is uneven, especially in places where health workers have limited time, equipment, or internet access.

The idea behind RetinaReach came from thinking about what screening looks like outside a perfectly controlled dataset. In a real workflow, the quality of the input matters just as much as the model that receives it.

Rather than treating AI as an answer machine, RetinaReach is designed to support the people doing the screening: help them capture a more usable image, make uncertainty visible, and send cases that need attention to a human specialist.

## The idea in one flow

1. **Capture or upload a fundus image.**
2. **Check image quality.** Look for basic signs that the image may be too dark, too bright, low-contrast, blurry, or low-resolution.
3. **Give useful feedback.** If the image needs another look, explain why and suggest a practical next step.
4. **Run a model only when one is configured.** The backend has an optional integration point for a separately hosted inference service.
5. **Keep the workflow reviewable.** Save screening records and flag records that need follow-up or have no completed model result.

The goal is not to replace an ophthalmologist. It is to make a screening workflow more transparent and easier to review.

## What is in this repository?

The backend starter currently includes:

- **FastAPI API** for the app to communicate with.
- **Account registration and sign-in** using password hashing and bearer tokens.
- **Image upload validation** for supported image formats and file-size limits.
- **Basic image-quality analysis** using brightness, contrast, and a simple sharpness proxy.
- **Screening records** stored in SQLite by default.
- **Review queue endpoint** for records flagged for review.
- **Optional model-service adapter** that can call a separately deployed inference API.
- **Interactive API documentation** generated by FastAPI.

The wider RetinaReach concept also proposes several features that are not automatically implemented just because they appear in the proposal. These include an EfficientNet-B0 diabetic-retinopathy model, calibrated uncertainty estimation, Grad-CAM evidence overlays, lesion localization, referral prioritization, and encrypted offline operation. Treat those as planned modules until they have been built, tested, and documented in the codebase.

## The main modules we want to build toward

### Retina Rescue
A quality gate that catches an image that may not be usable before it is passed to a model. The current backend uses simple image statistics. The proposal describes a more complete OpenCV pipeline using blur, illumination, and retinal-field checks.

### Confidence Contract
A model should not be treated as reliable just because it returns a number. The proposed system uses uncertainty estimation to identify cases that should be reviewed by a specialist. This requires a real model and proper calibration; it is not simulated by the current backend.

### Evidence Lens
The proposal includes Grad-CAM visualizations and lesion-localization overlays to help reviewers understand what influenced a model output. These visuals should be clearly labelled as model evidence, not as a diagnosis.

### Blind-Spot Lab
A planned robustness-testing area for examining how model performance changes under blur, contrast shifts, and other image distortions.

### Referral Optimizer
A planned way to prioritize the review queue so that higher-risk or more uncertain cases can receive attention sooner. It should support clinical workflows, not independently make clinical decisions.

### Offline Passport
The longer-term goal is to support low-connectivity settings. Reliable offline use requires more than a dashboard that loads without a network: model execution, data protection, storage, synchronization, and recovery all need to be implemented and tested.

## Getting started

### Requirements

- Python 3.11 or newer is recommended.
- `pip`
- A terminal and a code editor such as VS Code.

### 1. Download and extract the project

Download the backend ZIP and extract it to a folder, for example `RetinaReach-Backend`.

Open that folder in VS Code. The folder should contain `app/`, `requirements.txt`, `.env.example`, and this README.

### 2. Create a virtual environment

**Windows PowerShell**

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

If PowerShell blocks activation, you can use Command Prompt instead:

```bat
.venv\Scripts\activate.bat
```

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Create your environment file

Copy `.env.example` to `.env`.

**Windows PowerShell:**

```powershell
Copy-Item .env.example .env
```

**macOS / Linux:**

```bash
cp .env.example .env
```

Open `.env` and set `RETINAREACH_JWT_SECRET` to a long, random value. Do not commit your `.env` file to GitHub.

For local testing, the app can use its default SQLite database. The server reads environment variables from the process environment, so make sure your `.env` values are loaded before starting it. One easy option is to set the values in your terminal, or use a local environment-file loader of your choice.

**PowerShell example to load the simple `.env` file:**

```powershell
Get-Content .env | Where-Object { $_ -match '^[A-Za-z_][A-Za-z0-9_]*=' } | ForEach-Object {
  $name, $value = $_ -split '=', 2
  Set-Item -Path "Env:$name" -Value $value
}
```

### 5. Start the API

From the project folder, run:

```bash
uvicorn app.main:app --reload
```

When the server starts, open:

- **API docs:** http://127.0.0.1:8000/docs
- **Health check:** http://127.0.0.1:8000/api/health
- **Alternative API docs:** http://127.0.0.1:8000/redoc

Leave the terminal running while you use the API. Press `Ctrl + C` to stop it.

### 6. Try the API

The `/docs` page lets you try endpoints from your browser.

A simple first run:

1. Open `POST /api/auth/register`.
2. Create a test account with an email, display name, and password of at least 10 characters.
3. Copy the returned `access_token`.
4. Click **Authorize** in the docs and enter `Bearer YOUR_TOKEN` if the interface asks for the full value.
5. Try `GET /api/me` to check the signed-in user.
6. Use `POST /api/screenings` to upload a test image. Include the image file, an eye value (`left`, `right`, or `unknown`), and an optional label.
7. Check `GET /api/screenings` and `GET /api/review-queue` to see the saved record.

Use non-identifying sample data while testing. The default database and uploaded images are stored locally in the `data/` directory.

## API routes

| Method | Endpoint | What it does |
|---|---|---|
| `GET` | `/api/health` | Reports whether the API is running and whether an inference URL is configured |
| `POST` | `/api/auth/register` | Creates an account |
| `POST` | `/api/auth/login` | Signs in and returns a bearer token |
| `GET` | `/api/me` | Returns the current account |
| `POST` | `/api/screenings` | Uploads an image, runs basic quality checks, and saves a record |
| `GET` | `/api/screenings` | Lists the signed-in user's records |
| `GET` | `/api/screenings/{id}` | Returns one of the user's records |
| `GET` | `/api/review-queue` | Lists records flagged for review |
| `DELETE` | `/api/screenings/{id}` | Deletes a record and its stored image |

Protected routes require this HTTP header:

```http
Authorization: Bearer YOUR_ACCESS_TOKEN
```

## Connecting a frontend

Run the frontend separately from this API. During local development, the API base URL is:

```text
http://127.0.0.1:8000
```

The backend allows a few common local frontend origins by default. If your frontend runs on a different port or domain, update `RETINAREACH_CORS_ORIGINS` in the environment to include its exact origin, then restart the API.

Example JavaScript for signing in:

```javascript
const API_BASE = "http://127.0.0.1:8000";

async function signIn(email, password) {
  const response = await fetch(`${API_BASE}/api/auth/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, password })
  });

  const result = await response.json();
  if (!response.ok) {
    throw new Error(result.detail || "Could not sign in");
  }

  return result;
}
```

For image uploads, send `FormData` and do not manually set the multipart `Content-Type` header; the browser needs to add the boundary. The backend ZIP's `README.md` includes a fuller upload example.

## Optional: connect a model service

The backend does **not** contain a trained diabetic-retinopathy model. It includes an adapter for a separately hosted model API.

To configure it, set `RETINAREACH_INFERENCE_URL` to your service endpoint. The adapter sends the uploaded image in a multipart field called `file` and expects a JSON response shaped like this:

```json
{
  "status": "complete",
  "prediction_label": "model output label",
  "prediction_confidence": 0.82
}
```

That example shows the integration format only. It is not a prediction, a recommended threshold, or proof of clinical performance. The service you connect must be evaluated on appropriate data, and its limitations and intended use should be documented. The current quality gate skips model inference when its heuristic result is `review` or `recapture`.

## Data and privacy

By default, the backend stores the SQLite database and uploaded images in `data/`. That is convenient for development, but it is not a complete patient-data security setup.

- Use fictional or non-identifying data while developing and demoing.
- Do not upload real patient images unless you have the required consent, permissions, and an approved data-handling process.
- Do not deploy with the example JWT secret.
- Use HTTPS, secure storage, access logging, backups, retention rules, and a security review before handling sensitive data.
- The current starter does not implement email verification, password reset, rate limiting, or a complete production security workflow.

## Current limitations

A few things are intentionally stated plainly:

- Image-quality scoring is a basic heuristic, not a clinically validated quality assessment.
- The backend does not train or bundle an EfficientNet-B0 model.
- Disease predictions, calibrated uncertainty, Grad-CAM overlays, lesion localization, referral optimization, and full offline operation are not included as completed capabilities in this starter.
- The API and frontend still need to be integrated and tested together.
- This starter has not been independently validated for clinical use or production security.

These are build milestones, not reasons to hide the gaps. Keeping them visible makes the project easier to develop responsibly.

## A note on the approach

The part of RetinaReach I care most about is the workflow around the model. A screening tool should be able to say, “This image isn't good enough yet,” explain why, and ask for human review when the system is unsure. A clean score or an impressive heatmap should never be confused with clinical certainty.

That's the standard the project is aiming for.
